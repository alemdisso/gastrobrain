How to Run a Retrospective
Methodology note (from 0.2.7 onward): Per-issue weighted actual days and point-to-time ratios are no longer used. Story points are relative complexity units, not time units. The only velocity metric is sprint-level: pts delivered ÷ actual days. Per-issue tables record estimated pts and binary completion status only.
  1. 1

    Establish Sprint Boundaries

    Use the commit log to identify the sprint date range: git log --format="%h %ad %s" --date=short develop | head -30. Confirm with the developer — commits are a proxy, not the truth.

  2. 2

    Fetch Issue Data

    Collect estimated points from GitHub Project #3 (source of truth): gh project item-list 3 --owner alemdisso --format json --limit 100. For issues not in the project board, use the sprint planning doc estimate.

  3. 3

    Interview the Developer (CRITICAL)

    Before interpreting data, ask about: sprint boundaries; rest vs no-commit work days; hidden work (device testing, design thinking, planning); unplanned work context; efficiency drivers; blockers or friction.

  4. 4

    Calculate Sprint Metrics

    Actual days = confirmed working days • Pts delivered = sum of est pts for all completed issues • Velocity = pts ÷ actual days • Expected days = planned pts ÷ 6.5 • Sprint result = Under / On target / Over

  5. 5

    Document in This File

    Add a new section with: issue table (Issue, Title, Type, Est Pts, Status) • Sprint Performance table (planned, delivered, actual days, expected days, velocity, result) • Working pattern (commit timeline) • Lessons.

Key Insights

Velocity & Calibration

  • Cruising velocity is 30 pts/week — validated across 0.1.7b–0.2.4 (10+ consecutive sprints at 26–48 pts/week)
  • Velocity step-change is real — early sprints (0.1.2–0.1.6) averaged 1.1–3.0 pts/day; post-0.1.7b sustains 5.6–9.0 pts/day. Drivers: codebase maturity, Claude Code, accumulated infrastructure, developer proficiency
  • Sprint ratio depends heavily on work type — don't use one sprint's ratio to predict another sprint's performance
  • Small UX fix sprints inflate story-point velocity due to the 1-pt Fibonacci floor. Don't recalibrate cruising from UX-fix-heavy sprints
  • Code Health sprint profile reliably executes at execution-mode velocity (~36–40 pts/week) — size those milestones accordingly, not at cruising
  • Pure architecture sprint is the fastest velocity profile (0.2.12: 147 pts/week) — no UI/L10N/mobile overhead; mechanically predictable with defined DAO/component boundaries. Size pure-architecture sprints at 60–80+ pts/week, not at cruising or execution mode
  • Post-crisis investigation transfers directly to planned sprint velocity (0.2.11) — emergency sprints that force deep subsystem investigation give the next planned sprint zero debugging phase on directly related issues. Same 0.10x execution profile as post-usage bugs
  • Solo estimation without Estimation Poker anchors conservative (0.2.11/0.2.12) — board estimates diverged from sprint plan by 1–8 pts per sprint; mechanical refactor tasks over-estimated by 1.5–2× without collaborative calibration. Periodically revisit board estimates or run a pre-sprint sanity check
  • Four consecutive well-under sprints (0.2.11–0.2.14) may signal a new plateau, not just isolated accelerators. Velocity has decelerated each sprint (119 → 147 → 96 → 64.8 pts/week) but 0.2.14 is still 2.2x the 30 pts/wk cruising baseline. If 0.2.15 — a sprint without a major pattern-establishing anchor — also lands well above 30, reconsider whether cruising velocity has structurally shifted post-0.2.10 due to accumulated reusable infrastructure (IngredientParserSection, _SectionExpansion, showGastrobrainBottomSheet, hub-and-spoke screens)

Planning & Scope

  • Sprint plan specification quality is the primary velocity multiplier — writing the exact file+line fix location eliminates the debugging phase entirely
  • Scope discipline is as powerful as execution skill — selecting 13 of 32 available points (0.1.10) enabled clean 2-day execution; the deferred 19 pts would have diluted focus without user-facing benefit
  • A planning day (no commits) pays for itself within the first hour of Day 1. Pre-defined acceptance criteria = zero mid-sprint scope exploration
  • Dependency chain compounding is a planning tool, not an accident — actively identify "free ride" issues and schedule them immediately after their enablers
  • Linked issues estimated separately overstate total work — when issues share the same deliverable or redesign away each other, estimate the umbrella issue only

Execution Patterns

  • First-screen polish creates patterns; subsequent screens harvest them — 8x difference between #258 (first screen) and #259 (second screen) in 0.1.7b
  • "Real-life QA sprint" is a repeatable sprint type — intensive app usage (2 days) → issue discovery → batch fix. App usage days are a specification phase, not idle time
  • Post-usage bugs execute at 0.10x flat rate regardless of point estimate — root cause is known before the editor opens; no debugging phase needed
  • Within-sprint pattern compounding is the fastest reuse mode — #312 (3 pts) completed in 45 minutes using #311's dialog pattern built 3 days earlier in the same sprint
  • Batching similar small issues on a focus day with deep, uninterrupted time is multiplicative — 6 UX issues in one session, no context switching
  • The pattern escalator compounds across issue chains (0.2.13) — when one issue builds a widget, the next consumes it and establishes a higher-order template, and subsequent issues repeat mechanically, each link is faster than the prior. Estimate the anchor at full complexity; discount each follow-on 60–80% at planning time. The escalator only works when the anchor ships first.
  • Pattern escalators repeat across sprints with different chains (0.2.14) — 0.2.13's chain was #371→#370→#385-387 (within one sprint); 0.2.14's chain was #391→#396→#397 (within one day, with #396 also reusing 0.2.13's RecipeDetailsScreen/IngredientParserSection patterns from two sprints back). Anchor-ships-first → consumer-reuses-immediately → follow-on-reuses-consumer is now a repeatable execution mode, not a one-off

Validation & Quality

  • "Committed ≠ validated" is a recurring failure mode (0.1.12, 0.2.2) — fast execution without device testing creates deferred work, not completed work. "✓ Tested on device" must be a non-optional AC item for data-facing or display-ordering fixes
  • "100% completion" can mask validation debt — all points closed but follow-up issues emerge from skipped device testing
  • Real seed data is a distinct integration test category — 0.2.1's first real recipe dataset exposed two P0 import bugs that existed undetected through 50+ sprints of synthetic-fixture testing
  • Migration bugs have two prices: symptom and root cause — always review the runner's detection strategy, not just the failing migration. "Does this fix hold for the full range of possible DB states?"
  • The 101+ migration namespace is now mandatory — prevents numbering collisions with legacy schema versions. Documented in DATABASE_MIGRATION_WORKFLOW.md
  • "Device-tested, issues found and fixed" is now the expected outcome for UX sprints (0.2.14 #396) — 0.2.13 flagged device testing as non-negotiable after a post-merge bug slipped through 2,088 passing tests; 0.2.14's #396 (the largest single-day change in the diary at ~4,350 lines) was device-tested and fixed before the day ended. The AC item is working — but "lines changed" for such issues includes fix-forward iteration, not just first-pass code

Tooling & Environment

  • Hidden tooling overhead can be sprint-wide and massive (0.1.5: 2 full days = 29% of actual time, zero trace in commits). Add 25–35% buffer for mobile/UI sprints with testing phases
  • Windows Defender can block Dart/Flutter network access during release phases — add firewall exceptions to the new-machine checklist; check Defender first when Dart mysteriously stops working
  • adb/Android Studio friction is a recurring theme — accept VS Code as primary debug tool; don't invest more time in AS config
  • External design tool time (Recraft, Figma) leaves no commit trace — account for it explicitly in effective-day calculation during retrospective, same treatment as planning days
Estimation Guidelines

Before Estimating

  1. 1

    Identify infrastructure work explicitly

    New test patterns needed? → Add a separate "infra" task. New utilities or helpers? → Don't hide in the feature estimate. This is the main source of estimation errors.

  2. 2

    Audit blast radius before estimating removals

    Run a grep for the symbol being removed. If it appears in >5 files, it's a refactor (3–5 pts), not a chore. If it's an enum used throughout the codebase, estimate accordingly.

  3. 3

    Check commit history for similar past work

    High commit count in similar issues = add buffer. 10+ commits on a "1-day" estimate = the issue is likely underestimated.

  4. 4

    Identify which calibration bucket applies

    Use the type-based calibration table above. Distinguishing "extend pattern" (0.07–0.12x) from "create pattern" (1.0–1.5x) is the highest-value estimation decision.

  5. 5

    Consider batching small tasks

    Group related <30-line one-liners as a flat "quick wins block." Estimate individually only when tasks require genuinely different mental contexts.
